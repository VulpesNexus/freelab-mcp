# Architecture

## Two processes

```
AI app (Claude Code, Claude Desktop, …)
   │ MCP over stdio
server/freelab_mcp        ordinary Python 3, the mcp SDK (FastMCP)
   │ newline-delimited JSON over TCP, 127.0.0.1 only, one request per connection
listener/freelab_listener.py   inside FontLab (Python 2.7 in FontLab 7)
   │ FontLab Python API: fontlab (fl*), fontgate (fg*)
FontLab
```

The split keeps every FontLab call in one small file that can be read in a sitting and tested with fakes, and lets the server use a modern Python and the MCP SDK, which FontLab 7's Python 2.7 cannot run.

## Listener

- **Main thread only.** A `QTimer` polls a non-blocking socket every 25 ms, so every FontLab call runs on FontLab's main thread. A long request keeps FontLab busy until it ends. This follows the Glyphbridge finding that FontLab gives background threads no CPU while it idles ([PRIOR-ART.md](PRIOR-ART.md)).
- **Not re-entrant.** Qt fires timers inside nested event loops, such as a modal dialog opened by `run_python` code. A tick that arrives while a request runs returns at once, so the request in progress is neither dropped nor joined by a second one.
- **A real module.** Run as a script, the file loads itself as the module `freelab_listener` and starts from there, so the running listener's globals are not FontLab's script namespace. FontLab 7 has a preference, `python.clear_context`, that is on by default and presumably empties that namespace between runs (unverified). The listener object itself is kept on the `sys` module. Running the script again stops the old listener and starts a new one.
- **Never raises into FontLab.** The timer callback catches everything, `SystemExit` and `KeyboardInterrupt` included, and prints the first error of each kind in the *Output* panel; `run_python` does the same for the code it runs.
- **Bounded.** At most 16 clients at once, 4 MB per request, and 5 seconds for a client to send its line. A reply goes out without blocking, at most 4 MB per tick, and a client that has not taken all of it within 10 seconds is dropped: a blocking send from the timer once held FontLab up to 5 seconds behind a client that stopped reading. A reply over 64 MB is replaced by a `too_large` error. At most 8 connections are accepted per tick. A peer outside the loopback is closed unanswered (the socket listens on `127.0.0.1` only, so none should arrive), and after 20 requests with a wrong token within 10 seconds every new connection is closed unanswered for 5 seconds (clients already connected are not dropped).
- **Version-neutral source.** The file is valid Python 2.7 and Python 3; the test gate runs it under both. Text from FontLab or the system that is not UTF-8, such as a cp932 path in a Python 2 traceback, is decoded with replacement rather than allowed to break a reply.

## Discovery and authentication

On start the listener writes *%LOCALAPPDATA%\FreeLab\listener.json*: its port, a random 128-bit token, its PID, and its version. The server reads that file for every call and sends the token with every request; the listener compares it in constant time. The token keeps out what cannot read that file: other users' processes, and web pages (the endpoint is not HTTP, and a page cannot read the token). Any program running as the same user can read it, as the server does on every call, so the token is no barrier against those. Outside Windows the folder and the file are created readable by their owner only. On Windows that mode does nothing, so since 1.2.0 the file is born with a protected access list of one entry: full access for the user the listener runs as (the user's SID from the process token). It is made by `CreateFileW` with that list in its `SECURITY_ATTRIBUTES`, shared with nobody, and written through that handle, so no other account ever holds it open (before 1.2.0 was proven live, the list was set after the file was made, which left a moment when an inherited list applied: Codex, 2026-11-19). Nothing is inherited from the folder, so a `FREELAB_STATE_DIR` in a folder others can read no longer shares the token, and administrators are left out too. When Windows cannot do that, the file is made the ordinary way and the list set afterward (`SetFileSecurityW`); the listener says so in the *Output* panel, and `ping` reports why under `state_file_private` (`true` only when the file was born private). The file *opened.json* beside it, the fonts `open_font` opened, is made the same way. The default port is 47761; if it is taken, the listener takes any free port and the state file says which. When the listener stops, it deletes the state file, unless a newer listener has already replaced it. `FREELAB_STATE_DIR` moves the file, which the tests use.

## Protocol 1

Request, one line of JSON:

```json
{"protocol": 1, "id": 7, "token": "…", "deadline": 1793961600.5, "op": "glyph", "args": {"name": "A"}}
```

Reply, one line: `{"id": 7, "ok": true, "result": …}`, or `{"id": 7, "ok": false, "error": {"code": "no_glyph", "message": "…"}}`. The `id` is echoed only once the token is accepted. `deadline` is optional: seconds since the epoch after which the client has given up, so a request FontLab only reaches later is refused (`expired`) instead of run unseen. The server sets it on every call. A protocol change bumps the number in both halves; the server refuses a listener that speaks another one.

Listener error codes: `bad_json`, `bad_request`, `bad_token`, `bad_protocol`, `expired`, `unknown_op`, `bad_args`, `too_large`, `not_in_fontlab`, `no_font`, `no_current_font`, `no_such_font`, `ambiguous_font`, `font_mismatch`, `no_glyph`, `no_layer`, `no_master`, `no_class`, `wrong_side`, `class_name_clash`, `no_pair`, `no_outline`, `metrics_expression`, `name_taken`, `glyph_in_use`, `unicode_taken`, `no_anchor`, `no_feature`, `history_failed`, `not_kept`, `not_in_front`, `history_moved`, `nothing_to_undo`, `not_found`, `unexpected_type`, `unreadable`, `unserializable`, `unsaved_changes`, `quit_in_progress`, `risky_mode_off` (a risky action without `risky: true`; it replaced 1.1.0's `not_opened_here`), `dialog_changed` (`answer_dialog`'s dialog has another title; from the server, also a question no longer shown as it was at the time of the click, so nothing was clicked), `no_button`, `file_exists`, `unavailable`, `ambiguous_window`, `known_crasher` (`open_font`: a file FontLab 7.2 crashes on), `cannot_copy` (no fixed copy of it could be made), `failed`, and `exception`, which carries the traceback. The client adds `not_running`, `bad_state`, `timeout`, `connection`, `empty_reply`, `bad_reply`, and `too_large` (a request over the listener's 4 MB, refused before it is sent). The server's tools add `bad_args`, `listener_not_running` (FontLab runs without its listener), `not_found` (no FontLab program), `no_listener` (FontLab started, its listener did not answer), `save_prompt` (FontLab asks whether to save a font, and waits for the user), `dialog_open` (it asks something else), `still_running` (FontLab asked to close, still open), `not_opened` (a font not open by the end of the wait), `still_open` (a font asked to close, still open), `not_saved` and `not_exported` (no file changed by the end of the wait), for `screenshot` with `source="screen"`, `unavailable`, `not_found`, `ambiguous_window`, `too_large`, and `failed`, and, for the window tools, `still_busy` (`wait_idle` timed out) and `failed` (an action raised). The window tools' listener codes are `ambiguous_window`, `ambiguous_control`, `wrong_kind` (a control of another kind than the tool takes), `disabled`, `unavailable` (hidden, read-only, or a link out of FontLab), `dialog_open` (a dialog waits: only it can be driven), and `busy` (an earlier action, or a window's work); an action checked again when its timer fires and not done says why under `code` (`changed`, `disabled`, `lost`, `listener_stopped`, and the codes above), and the tool reports it as its error. Risky mode is checked first by the server (`risky_mode_off`, see [RISKY.md](RISKY.md)) and again by the listener.

## Fonts by name

Every font op takes `font`: an id from `fonts` (FontLab's `fgPackage.id`, an integer, or the same digits as text, which may also be a font's name), a path (compared with separators and case normalized), a PostScript name, or a full name. No match is `no_such_font`, with the open fonts listed; two matches are `ambiguous_font`, with their ids. The reads fall back to the font in front without `font`; the writes and `undo` refuse (`bad_args`): a change never lands on a font the caller did not name. They also take `font_name` (a path or name) to confirm an id, since FontLab may give an id to a font opened after another was closed (`font_mismatch`). On the MCP side an id is a strict integer: `true` is no font.

## Writes

Each write op works in the same order, and stops at the first refusal with nothing changed:

1. **Check everything.** The font, glyph, layer, master, and every argument are validated, and the change is planned: a pair's sides are resolved against the master's kerning classes, metrics computed from the layer's ink box, a rename checked against kerning, classes, and feature code, a component glyph planned master by master. A write that would change nothing returns `changed: false` and records nothing.
2. **Bring the font forward, and record it first when Undo needs it.** FontLab gives a step a title only when its font is in front (a step of a font behind another shows blank in the *History* panel and in *Edit > Undo*, live), so the font is brought to the front for the write, as a click on its tab does, and the font that was in front is put back once the write is over, whatever became of it; a font with no window tab is written behind, and the reply's `history.warning` says its step has no title. A step of FontLab's *History* records each object as it is after the change, and Undo puts back each object's state before that step; an object with no state yet stays as written ([FONTLAB7-API.md](FONTLAB7-API.md#history-notifications-and-layers-found-live-2026-11-14)). So the first write to a font in a listener session, and a write after an Undo back to the font's first state, record the font (and the glyphs the write changes, when they have no state) as a step of its own, titled "… (before)". When FontLab cannot record it, nothing is changed (`history_failed`). The client's deadline is checked here too (`expired`).
3. **Change, then read back.** The read-back allows what FontLab does on its own: whole advance widths and kerning values, and a line break at the end of feature code. What FontLab did not keep, or a change that raised, is put back and read back again: then the write is refused (`not_kept`) and the font is as it was. When it cannot be put back, the change is recorded as the write's History step and the font marked modified all the same, and the refusal carries that step under `data.history`: a change is never left outside the History, unmarked.
4. **One step, marked modified.** `notifyChangesApplied(title, [font, glyphs…], True)` records the change as one step titled "FreeLab MCP: …", and `setFlag(2, True)` marks the font modified, since a script's change alone leaves FontLab free to close it without asking. The reply holds the values before and after, and `history`: `recorded`, `marked_modified`, the font's `history_state`, and a `warning` when marking failed. When FontLab's History refuses the step, the write is no success (Codex, 2026-11-19): the change is put back and read back, and the write refused with `history_failed` and nothing changed; when it cannot be put back (a deleted glyph comes back only through Undo), the font is marked modified and the refusal says the change stays, with the History status under `data.history`.

`undo` brings the named font to the front first, since FontLab's *Edit > Undo* acts on the font in front, and puts the font that was in front back afterward, also when it refuses (unless `keep_in_front`); a font with no window tab is refused (`not_found`). With a write's `history_state` as `expected_state` and its `title` as `expected_title`, it refuses (`history_moved`) unless the font's History is still at that state and the step the *Undo* action names is that write's: a step that records only glyphs (a write's leftover "(before)", or a user's edit) leaves the font's state as it was, so the state alone cannot tell. It triggers FontLab's own *Edit > Undo*, checks through the *Redo* action that the step it named was taken back (and, when *Redo* named a step of that title already, that the font's state moved), and takes the write's own "(before)" step back with it, so each write is one `undo`; it reports the steps undone, the one *Undo* would take back next, and the History state before and after.

The server gives writes 120 seconds (`WRITE_TIMEOUT_S`) and reads 10: a History step waits on the Windows clipboard when another program holds it open (17 s a step, seen live).

A tool that waits for the outcome of what it asked (`open_font`, `close_font`, `save_font`, `export_font`, `answer_dialog`, `quit_fontlab`, and `launch_fontlab` once the listener is there) keeps waiting past its `wait_s` while FontLab's process runs but its listener does not answer, up to 300 seconds more (`SILENCE_MAX_S`), and looks 5 seconds longer (`SILENCE_GRACE_S`) once FontLab answers again: FontLab held by a clipboard another program holds answers nothing for 20 to 60 s at a time, and what it was asked still happens. Silence is a request that timed out, or a connection refused while FontLab runs (the listener refuses connections once its queue of 8 is full); a connection refused once FontLab is gone ends the wait at once. A tool that gives up while FontLab is silent says it does not know the outcome and for how long FontLab did not answer. `wait_idle` counts silence as work, within its own `timeout_s`; an action's tool (`click` and the like) returns at once with the action still `running` and leaves the wait to `wait_idle`.

## Error model

- **A failed read is never an empty value.** Each property read is guarded; one that fails is `null` in the reply and listed under `unreadable` with its exception. A reply without `unreadable` read everything it shows.
- **Native containers are not indexed or iterated.** Only real Python lists and tuples that FontLab returns are walked; anything else is refused with `unexpected_type`. A wrong call on a native FontLab object can crash FontLab where `try` cannot catch it (reported for FontLab 8 by Glyphbridge).
- **Qt values are converted by class name** (`QRectF`, `QPointF`, `QTransform`, …); other native objects are returned as their `repr`, never probed for methods.
- **A null check that fails is an error.** If FontLab cannot say whether an object is null, the operation stops with `unreadable` instead of calling into a possibly null object.
- **The server never invents state.** Listener errors become MCP tool errors with the listener's code and message. Its tools are async and make the socket call in a worker thread, so the server keeps answering the AI app while FontLab works.

## Tests

The fakes in *tests/fakes.py*, and in *tests/widgetfakes.py* for the Qt widgets the window tools drive, are spies: each fake FontLab or Qt object allows only the members the listener is documented to use, and raises `SpyViolation` (a `BaseException`, which the listener's `except Exception` cannot swallow) on any other member, on a subscript, or on iteration. A new FontLab call therefore fails the tests until it is added to the fakes and to [FONTLAB7-API.md](FONTLAB7-API.md). The socket tests run the real listener on a real loopback socket; the server tests run the real MCP tools against it. Every test also fails if the listener caught and recorded an error along the way. The guards added after the first independent review were mutation-tested: each was removed from a throwaway copy in turn, and the suite failed every time.
